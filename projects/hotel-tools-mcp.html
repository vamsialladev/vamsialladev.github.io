Case study · stage 7

Hotel Tools MCP Server

The hotel group's tools for any MCP client, such as Claude Desktop or Claude Code: the caller's role decides which tools even exist and which fields come back, another hotel group's data looks like it isn't there, and every call lands in a tamper-evident audit log.

Independent project: a simulated client engagement for the same fictional hotel group as the other stages, with synthetic data. Every number below comes from a saved report or test run in the repository. A second synthetic hotel group exists only to prove tenant isolation.

Live: a public, read-only copy at https://hotel-tools-mcp.vercel.app/mcp, connected as one made-up guest with no key and 10 calls a minute. On 2026-10-28 it passed 8 of 8 checks with the official MCP Python SDK client. How to connect →

01 · Problem

Problem

Every new AI client (the stage 2 agent, Claude Desktop for managers, a future guest assistant) would re-implement the same booking lookup, the same $50 front-desk credit limit, the same “never read another guest's booking” rule and the same defence against instructions planted in documents. Copying those rules into every client is how one of them ends up without them. IT's biggest worry in discovery was someone tricking the AI into doing something.

02 · Approach

Approach

  • One server, seven typed tools: policy search (stage 1's search, copied at v1.6.0 and checked in CI), booking lookup, activities, booking requests, credit requests, credit approval, audit log.
  • Roles by API key: guest, front desk, manager, auditor. One server process serves one key and registers only that role's tools, and every call is checked again.
  • Field views and limits: a guest sees six fields of their own bookings only; front desk issues credits up to $50, above that waits for a manager; the auditor reads the audit log and nothing else.
  • Tool results are data: sentences that read like instructions to an AI are removed from passages, booking notes and activity descriptions before they leave the server.
  • Audit: one record per call (allowed or not) with role, hashed subject, tool, a hash of the arguments, status and the previous record's hash, so editing a line breaks the chain.

05 · What the eval taught me

What the eval taught me

The first run scored 97%. The three failures were one case run three times, and the server was right: an auditor of the second hotel group had no audit records yet, so my check compared an empty list with the expected group. An empty result can pass or fail a check for the wrong reason, so the check now fails on an empty list and the case first makes a call in each group.

07 · Engineering

Engineering

  • Tests: 81, 90% coverage, including every role × every tool and a stdio round trip with the server as a separate process, the way Claude Desktop starts it.
  • CI: ruff, pytest, the eval gate at 100%, a check that the copy of stage 1's search matches its pinned commit, pip-audit, a link check and gitleaks.
  • SDK: the official MCP Python SDK's MCPServer, the class formerly called FastMCP.
08 · Business case (projection)

Business case (projection)

A projection, not a result: each new AI client connects to tools that already enforce the hotel's limits instead of re-building them, and IT gets one place to grant, limit and audit AI access. A pilot would measure time to connect a new client and the denied calls and removed instructions per week in the audit log.

09 · Limitations

Limitations

  • Demo authentication: API keys in a local file. docs/AUTH.md shows how OAuth / SSO replaces it.
  • JSON files and one process per key: fine for a pilot, not for scale (see Design at scale).
  • The injection guard is pattern-based: it catches the phrasings in the eval, not every possible one. Clients are also told, in the server instructions and in every result, that results are data.
  • No PMS integration: requests and credits are recorded, never posted.
  • The public endpoint's rate limit and audit log live in each running instance, so they reset on a cold start (decision 15).
10 · What's next

What's next

  • OAuth tokens from the hotel's identity provider instead of API keys (the public endpoint already speaks Streamable HTTP)
  • Postgres with row-level security as a second wall between hotel groups
