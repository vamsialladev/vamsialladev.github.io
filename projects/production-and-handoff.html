Production & Handoff

Two live AI apps made ready for a hotel group to run: the gaps the evals found fixed and measured, personal data out of the logs, budgets that fail CI, monitoring that knows “asleep” from “down”, and a handoff package their own team can work from.

01 · Problem

A demo is not a service

Both apps worked, and the eval harness said so. It also said where they didn't: a front-desk agent who types in Spanish was turned away before the model saw the question; “there's smoke coming from under a door” got no manager warning; a guest who wrote to the wrong hotel's inbox got the wrong hotel's answer.

And nothing about running them was ready for someone else: logs vanished on every restart and kept names as typed, anyone could do anything, a cost spike had no off switch, and the only monitoring was me opening the app.

02 · What changed in production

What changed in production

Every fix started with new held-out cases committed before the code, so the “after” can't be the result of tuning to them. Numbers are live re-runs, Claude Haiku 5.5, 3 runs each, 2026-10-15.

The headline numbers didn't drop: the assistant's answer accuracy went from 98% to 100% (162/162; the Spanish question q37 now passes) at a 95th percentile of 2.93 s and $0.18 per 1,000 questions. The agent kept every hard gate at 100%, with correct tool use 96% → 100%, citations 94% → 100% and $1.30 → $1.24 per 1,000 emails.

  • Persistent, private logs: every request goes to Postgres (Neon) or SQLite, one table shared by both apps. Emails, phone and card-like numbers and names are removed, and booking IDs hashed, before anything is stored; records are deleted after 30 days. Tests plant personal data in every field and fail if any survives.
  • Staff sign-in: the public demo stays open in a labelled Demo mode; a Staff role (lockout, idle sign-out) unlocks reporting an answer for review. A real client would use their own SSO; the switch is documented.
  • Budgets and resilience: p95 and cost-per-1,000 budgets for each app, checked by the eval harness in CI; 30-second timeouts with retries; a kill switch that stops every model call.
  • Monitoring: an owner-only Operations page (requests, errors, latency, cost per day, budget status) and a daily GitHub Action that reads Streamlit Cloud's status, so a sleeping free app never pages anyone and a broken one opens an issue.
03 · The handoff package

The handoff package

Everything the hotel's IT and operations teams need, in Markdown in one repo, built from the real code and linking back to it:

  • Architecture across all three systems: data flows, where each secret lives, what is logged and what is redacted.
  • Eight runbooks, each with how you notice it, the steps and how to check it worked: API outage, cost spike, a bad or harmful answer, prompt injection, an app asleep or down, rotating secrets, restoring logs, adding a property's documents.
  • SLOs and budgets with how each is measured and alerted, and an error-budget policy.
  • Plain-language guides for front-desk and guest-services staff, and an admin guide.
  • A readiness checklist with an evidence link per item (owner-only items left for the owner) and a 30/60/90-day plan for the client team.

04 · What production taught me

What production taught me

  • A fixed rule wasn't a fixed answer. After the safety rule caught “smoke under a door”, the model still answered it with the smoking policy and a $250 cleaning fee. Emergencies now skip the model entirely.
  • The prompt-injection gap I found had no warning sign. A held-out note “to the automated system” matched none of the agent's patterns, so it passed the planted request on to a manager. Planted text is now removed before the model reads the email; I wrote three new injection cases first, and they passed before the fix too: that case was flaky, not systematic.
  • Every fix has a price, and I report it. With the planted “6 PM check-out” gone, one held-out reply stopped volunteering the guest's Platinum late check-out (key facts 3/3 → 0/3). Safe and correct, less specific: reported, not tuned.
  • The new timeout caught a real stall. In the first live run one streamed answer froze for 30 seconds; the eval driver now counts a failed call as a failed answer instead of stopping.

06 · Engineering

Engineering

  • Tests: assistant 378 and agent 276 (97% coverage each), plus 8 per app that run against a real Postgres in CI; the harness 92; the health check 12, including asleep vs down.
  • CI: each app gates its release's saved live run with latency and cost budgets; the harness checks that the previous releases fail against the new baselines, so a rollback would be caught.
  • Releases: assistant v1.6.0, agent v1.1.0, harness v1.2.0, handoff v1.0.0; docker compose up runs each app with its own Postgres.
  • Cost: about $0.89 in API spend for both stages, almost all of it live eval runs.
