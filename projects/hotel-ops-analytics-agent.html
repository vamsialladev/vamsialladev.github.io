Case study · stage 8

Hotel Ops Analytics Agent

Managers ask the bookings database questions in plain English and get a table, a chart and a short answer, always with the SQL that produced it. A daily check finds anomalies and posts them to Slack.

Independent project: a simulated client engagement for the same fictional hotel group as the other stages, with synthetic data. Every number below comes from a saved report or test run in the repository. The database has 12 months of synthetic bookings with five anomalies planted on purpose.

Try the live appCode on GitHub

Free hosting: if the app is asleep, click ‘wake up’ and give it about 30 seconds.

01 · Problem

Problem

The revenue manager said a custom question means “half a day” of pivot tables, and that a number without its query won't go in a board pack. A rate loaded wrong for a week went unnoticed until the month-end report.

02 · Approach

Approach

  • Plan: Claude Haiku 5.5 returns structured JSON: a clarifying question (only for “our hotel” without a name, or occupancy without a date), a refusal, or one SELECT and a chart.
  • Guard: every query is parsed before it runs: one SELECT, allowlisted tables, a LIMIT of at most 500, and guest names, emails and phones only for the manager role. The connection is read-only underneath, with a 3-second limit.
  • Answer: a second call writes 1–3 sentences from the rows; numbers that aren't in the result are flagged. The SQL is always on screen.
  • Daily check: five SQL rules (occupancy drop, cancellation spike, refund spike, activity no-shows, rate error) against the previous 28 days, no model, posted to a Slack incoming webhook by a scheduled GitHub Action.

06 · What the eval taught me

What the eval taught me

The first recorded run scored 84%. Half the failures were the grader: the model answered “Beach Resort” where the reference said beach-resort, returned a full ranking with the right answer first, and gave a share as 34.21% instead of 0.342. I fixed the grader and re-scored the saved queries without calling the model: 84% → 92% on the same answers. The rest were real, and some were mine: my prompt told the model to ask for a time frame and used “cancellations” as the example, so it asked instead of answering.

Before any model run, a free check that every reference query passes the guard found a guard bug: COUNT(*) looked like SELECT * over the guests table.

08 · Engineering

Engineering

  • Tests: 49, 85% coverage: the guard, the read-only connection and time limit, the agent with the model replaced, each planted anomaly, the Slack job without network, and the app via Streamlit AppTest.
  • CI gates without an API key: every reference query passes the guard, the detector catches 5/5 on both years with at most one false alarm a month, and the saved dev run re-scores to the same verdicts.
  • API spend: about $0.15 for every eval run.
09 · Business case (projection)

Business case (projection)

A projection, not a result: a custom question in seconds instead of half a day, and a mispriced room caught in a day instead of at month-end. In this data the Suite was loaded at $50 instead of $515 for five nights, about $2,300 of lost revenue per room sold. A pilot would measure report hours per week and days from an anomaly starting to someone acting on it.

10 · Limitations

Limitations

  • SQLite only. Postgres via DATABASE_URL is designed (sqlglot can transpile the guarded SQL), not built.
  • Demo roles without sign-in. A real deployment would use the stage 7 tool server's roles or SSO.
  • I wrote the eval questions with the schema in front of me. A client's real questions will be messier.
  • Conversation history lives in the browser tab (session state), not a database. Stage 6 stores it in Postgres.
  • On Streamlit Cloud the request log and daily counters reset when the app restarts.
